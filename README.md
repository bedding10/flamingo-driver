# flaminGO Driver

Driver app for the flaminGO platform. Expo + React Native, same toolchain as
flaminGO Passenger.

## Ground rules

- The backend is the single source of truth. Every route and every socket event
  used here is listed in `DRIVER_API_MAPPING.md`, which was generated by reading
  the live NestJS source.
- No mock APIs, no invented endpoints, no trip states outside the Prisma enum.
- Missing server capabilities are recorded as gaps in `DRIVER_API_MAPPING.md`
  instead of being faked in the app.

## Setup

```bash
cp .env.example .env       # set EXPO_PUBLIC_API_URL
npm install
npm run typecheck
npm start                  # dev client
```

Native builds need `google-services.json` / `GoogleService-Info.plist` (Firebase)
and the Google Maps keys supplied as EAS secrets:

```bash
eas secret:create --name GOOGLE_MAPS_ANDROID_API_KEY --value ...
eas secret:create --name GOOGLE_MAPS_IOS_API_KEY --value ...
```

## Phase 1 addendum (approved decisions)

- **React Native 0.76.9 / Expo SDK 52** confirmed. No downgrade to 0.74: the
  passenger app is the reference environment and both apps share one EAS
  pipeline.
- **Application id `com.flamingo.driver`** on both platforms. It is a separate
  Firebase app inside the existing flaminGO project, so FCM tokens, Crashlytics
  and Analytics are separated from the passenger app. The passenger id is never
  reused.
- `src/config.ts` is the only file that reads the environment.
- Credentials live in secure storage only; MMKV holds non-sensitive cache.
- The socket reconnects on background -> foreground.

## Phase 2 - Authentication

Sign-in path, and the only one that exists:

1. `requestPhoneCode(phone)` - Firebase sends the SMS. The number is normalized
   to E.164 first (`+213...`), otherwise Firebase cannot resolve the SMS region
   and fails with 17006 even when Algeria is allow-listed.
2. `confirmPhoneCode(confirmation, code)` - verifies the code, then forces a
   fresh Firebase ID token.
3. `POST /auth/firebase { idToken, role: "DRIVER" }` - the backend verifies the
   token and returns `accessToken` / `refreshToken`. On a first login it also
   creates the driver record, so a new driver always starts at `PENDING`.
4. Tokens are written to `expo-secure-store` **before** any authenticated call.
5. `POST /auth/me` loads the account (the server exposes this as POST).

The server's local OTP endpoints are deliberately not wrapped: `requestOtp`
throws and `verifyOtp` issues no tokens.

### Approval gate

`ApprovalGate` wraps `DriverNavigator`, so every current and future signed-in
route is behind it. When `GET /driver/me` returns a status other than `APPROVED`
the driver sees the waiting screen with the real status and no ONLINE control -
the server rejects `POST /driver/me/availability` with 403 until an operator
approves the account.

A failed profile load falls back to the cached profile, so a dropped request
cannot lock out an already approved driver.

### Not in Phase 2

Profile editing, document upload, the map, availability and offers. They arrive
in Phase 3 and later.

## Phase 3 - Profile, vehicle and documents

Everything on these screens is transcribed from the server, field by field:

- `GET /driver/me` returns a nested `vehicle` object plus `documents`, `status`,
  `approved`, `rating`, `totalTrips`, `city` (name) and `cityId`.
- `PATCH /driver/me` accepts FLAT fields (`carMake`, `carModel`, `carColor`,
  `carPlate`, `carYear`, `rideClass`). The read shape and the write shape are not
  symmetrical, so they are modelled as two separate types instead of one guess.
- Only changed fields are sent. The server resets the vehicle verification to
  PENDING whenever an identity field differs, so resending untouched values would
  invalidate an already approved vehicle.
- Documents: `POST /driver/me/upload-url` -> PUT to storage -> `POST
  /driver/me/documents`. Registration always stores PENDING; only an operator
  changes that.

A driver under review reaches the onboarding stack (status, profile, documents)
and nothing else. Approved drivers reach the same profile and documents screens
from the main stack, so the file can be kept up to date later.

### Read-only on purpose

- **Phone number**: it is the identity Firebase authenticates. `PATCH /driver/me`
  would change it without re-verification and lock the driver out of the next
  login.
- **City and vehicle type**: their catalogues are `@Roles("STAFF")` endpoints with
  permission checks (`/cities`, `/vehicle-types`, `/vehicle-categories`), so a
  driver token cannot list them. No picker is invented over data the app cannot
  read.

### Backend gaps found in Phase 3 (recorded, not worked around)

1. `POST /driver/me/upload-url` returns a `readUrl` produced by
   `storage.signedReadUrl(...)`, which expires after 7 days, instead of
   `storage.readUrl(...)` which prefers a permanent `R2_PUBLIC_URL`. The document
   URL stored on the record therefore stops resolving after a week, in the app and
   in the review dashboard alike. One-line server change, deliberately not made
   here.
2. There is no endpoint to re-sign an existing document, and no endpoint to delete
   a wrongly uploaded one; a replacement is a new row.
3. No driver-readable catalogue for cities or vehicle types (see above).
4. `DocumentStatus` has no EXPIRED member, so document expiry cannot be modelled
   at all. Nothing in the app pretends it can.
